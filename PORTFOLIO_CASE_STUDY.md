# Portfolio Case Study — Relic Runner: Design-Led Vertical Slice Improvement

## Project overview
Relic Runner is a short 2D platforming vertical slice about collecting relics, activating joystick-controlled gates, and surviving enemy and hazard pressure across six compact levels.

## My role as Game/Systems Designer
My intended role is to analyze the existing game, identify player experience problems, define improvement goals, document systems, prepare balance data, plan playtests, and work with implementation support to make small modular changes. The goal is not to present myself as the sole engine programmer, but as a designer who can collaborate with programmers and use data to improve a playable game.

## Original game condition
The original workspace contains a polished class-style web prototype with movement, jumping, dash, relic gates, enemies, hazards, audio, VFX, six levels, and a win condition. It does not contain a standard Unity project structure despite the project prompt referencing Unity.

## Design problem
The game is playable, but the portfolio story is not yet clear. It needs documented design intent, balance rationale, measurable iteration criteria, and playtest planning. Without telemetry or a case-study structure, reviewers cannot easily see how design decisions were made.

## Design process
1. Audit the current loop, mechanics, content, architecture, and limitations.
2. Identify player experience problems and missing portfolio evidence.
3. Compare update proposals by player value, implementation size, and portfolio relevance.
4. Recommend a telemetry-led balance pass as the first update.
5. Prepare documents that make future implementation and playtesting reviewable.

## Implemented solution
Current implementation for this pass is documentation and project positioning only. Major gameplay implementation has not begun because the project owner requested inspection and proposal review before major changes.

## Balancing and iteration
Initial balance values have been catalogued in `BALANCE_DATA.csv`. Revised values are marked pending where real telemetry or playtest evidence is needed. No performance improvement percentages have been invented.

## Playtest results
Pending. No real player sessions have been conducted for this portfolio update yet.

## Final outcome
The project is now positioned for a design-led portfolio update. The next recommended step is to implement telemetry and completion summary features, then run a small playtest and revise balance based on observed data.

## Lessons learned
- A playable prototype is stronger as a portfolio piece when the design reasoning is visible.
- Telemetry should come before major tuning claims.
- Small modular updates are better than rebuilding an existing working slice.
- Clear documentation helps separate game design contribution from raw implementation effort.
